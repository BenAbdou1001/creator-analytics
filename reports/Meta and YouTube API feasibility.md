# Official APIs can replace Claude for two platforms

Yes. For **YouTube and Instagram, the official APIs can replace Claude's dashboard reading as the primary data-collection path**, and they should. Between them, the YouTube Data, Analytics and Reporting APIs supply **19 of the 23 YouTube catalogue metrics** directly, with RPM computable from them. The Instagram Graph API via "Instagram API with Instagram Login" supplies **23 of the 25 Instagram rows**, though story metrics live only 24 hours and Reels have no per-post follows. Both work for a single-owner, self-hosted app without App Review or Google verification, provided each self-hoster brings their own OAuth client. The gaps are real but narrow. YouTube's unique, new and returning viewers are not available. Neither is Instagram's account-level profile visits, its bio-link taps, or any follower identity list. YouTube impressions history cannot be backfilled earlier than 30 days before you create the Reporting job, and Instagram account metrics cannot be backfilled earlier than about 90 days. **Every day without a running sync is history lost for good**, so the connectors should ship sooner rather than later. TikTok and LinkedIn are different. TikTok's reachable API returns only lifetime public counters, and its app review rejects "private or personal use" apps. LinkedIn's member analytics API is open only to registered organizations. For those two platforms, exports and the existing MCP path remain the practical route. A further reason to move: both YouTube's and Meta's terms classify automated reading of logged-in dashboards as prohibited "automated means". The current Claude-driven path therefore carries account risk that the APIs remove. The recommended architecture adds per-platform connectors that map API fields onto existing `metric_key`s and call the existing `SyncService`. It also adds a `platform_api` SourceKind, BYO OAuth credentials with encrypted token storage, and an idempotent `creator-sync` CLI run daily. YouTube ships first.

## YouTube exposes almost everything, split across three APIs

No single YouTube API is enough. The Analytics API (AA, `reports.query`) supplies daily channel and per-video time series: views, watch time, subscribers gained and lost, average view duration and percentage viewed, demographics and revenue ([AA Metrics](https://developers.google.com/youtube/analytics/metrics)). The Data API v3 supplies current lifetime counters, metadata and the realtime subscriber count. That count is **rounded down to three significant figures above 1,000** ([Data API revision history](https://developers.google.com/youtube/v3/revision_history)). Thumbnail impressions and impressions CTR arrived only in the **Reporting API (RA) on 15 Jan 2026**, as `video_thumbnail_impressions` and `video_thumbnail_impressions_ctr` in the `channel_reach_basic_a1` report keyed by date and `video_id` ([AA/RA revision history](https://developers.google.com/youtube/analytics/revision_history); [RA channel reports](https://developers.google.com/youtube/reporting/v1/reports/channel_reports)). A search snippet suggested a matching AA "Reach metrics" section, but direct fetches of the AA metrics page did not show one. **Treat AA impressions as unverified and make RA the source of record.**

"Views" is unstable over time, and the archive needs to track that. Shorts views switched to counting every start and replay on **31 Mar 2025**, with the old count preserved as `engagedViews`. All public views switched to "from the first frame" on **27 Aug 2026**. Co-views on TV screens were added on **16 Nov 2026** ([AA revision history](https://developers.google.com/youtube/analytics/revision_history)). Re-querying old dates today can therefore return numbers that differ from values archived earlier. The connector should store `engagedViews` alongside `views` (a new `engaged_views` catalogue key) and should not overwrite earlier-archived facts silently. To separate Shorts from long-form, use the AA `creatorContentType` dimension (data from 1 Jan 2019). That dimension is absent from the RA user-activity reports and from AA's basic user-activity report, and whether `day,creatorContentType` is an accepted combination was not verified ([AA Channel Reports](https://developers.google.com/youtube/analytics/channel_reports)).

The subscriber identity list is technically available but should not be relied on. `subscriptions.list?mySubscribers=true` still exists at 1 quota unit, but Google warns that the number returned "might be limited" ([subscriptions.list](https://developers.google.com/youtube/v3/docs/subscriptions/list)). Reports that it is capped near 1,000 and limited to public subscriptions are folklore that the research could not confirm. No API lists unsubscribers. The existing `sync_relationships` path should stay fed by MCP or manual input, and API-sourced subscriber lists should be treated as partial at best.

## Instagram covers posts well but forgets account history after 90 days

Meta's late-2026 Instagram surface uses a "views + interactions" model on Graph API **v26.0 (released 29 Jul 2026)**. v21.0 expires on 21 Jan 2027, so the connector should pin v25 or v26 ([Graph API versions](https://developers.facebook.com/docs/graph-api/changelog/versions)). Most account metrics on `/{ig-user-id}/insights` now support only `period=day` with `metric_type=total_value`; only `reach` still offers `time_series` ([IG account insights](https://developers.facebook.com/docs/instagram-platform/api-reference/instagram-user/insights)). In practice, the connector issues one call per day and per metric group to build each daily series. Media insights include `reposts`, `reels_skip_rate` and `crossposted_views` (all Dec 2025), plus story `link_clicks` (Jun 2026) ([IG changelog](https://developers.facebook.com/docs/instagram-platform/changelog)).

The hard constraint is time, not coverage. Meta's Insights overview says **"User Metrics data is stored for up to 90 days"** ([IG Insights overview](https://developers.facebook.com/documentation/instagram-platform/insights)). Third-party connectors report six months to two years instead, and some report a 30-day-per-request cap ([Supermetrics](https://docs.supermetrics.com/docs/good-to-know-about-instagram-insights.md); [Fivetran](https://fivetran.com/docs/connectors/applications/instagram-business/troubleshooting/skipped-media-metrics-warning)). Plan around 90 days and fetch in chunks of 30 days or less. Media insights last up to two years, so a first-connect backfill can recover lifetime post metrics for older posts but not their daily curves. Stories are the sharpest edge. Their insights disappear after **24 hours**, and the `story_insights` webhook exists only under Facebook Login, not Instagram Login ([IG media insights](https://developers.facebook.com/docs/instagram-platform/reference/instagram-media/insights)). A once-daily job will miss some stories, so the connector needs a story poll every few hours or must accept partial story coverage. The catalogue's 730-day retention on the story rows describes Instagram's GUI, not what the API exposes. Instagram also exposes no follower or following edge, so follower identities stay outside the API entirely ([IG User reference](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user)).

## Auth and terms favour a bring-your-own-app model

Both platforms make a single-owner archive easy only if **every self-hoster registers their own developer app**. On Google, the trap is that an External project left in "Testing" issues **refresh tokens that expire after 7 days**, which breaks unattended sync. The fixes are Google's newer **"Personal mode"** OAuth client (only you, no verification, no warning screen, a one-time choice that cannot be changed later), or switching the consent screen to "In production" and clicking through the unverified-app warning, which is allowed under 100 users ([Google OAuth 2.0 overview](https://developers.google.com/identity/protocols/oauth2); [Google Cloud Help](https://support.google.com/cloud/answer/13464323)). Refresh tokens also die after six months unused, and each client is limited to 100 refresh tokens per account. A daily job and a "reuse the existing token" connect flow handle both limits. The scopes are `youtube.readonly`, `yt-analytics.readonly` and `yt-analytics-monetary.readonly`. Default Data API quota is **10,000 units per day**, with list calls at 1 unit, plus a separate bucket for `videos.batchGetStats` since Jun 2026. A channel with thousands of videos needs only a few hundred units per day, so no compliance audit is triggered ([Data API quota calculator](https://developers.google.com/youtube/v3/determine_quota_cost); [quota and compliance audits](https://developers.google.com/youtube/v3/guides/quota_and_compliance_audits)). No official AA or RA quota figures were found.

On Meta, "Instagram API with Instagram Login" on `graph.instagram.com` needs a Creator or Business professional account but **no linked Facebook Page**. It uses the scopes `instagram_business_basic` and `instagram_business_manage_insights`. It runs at **Standard Access**, which is "intended for apps that will only be used by people who have roles on them", so App Review and Business Verification are not required ([IG overview](https://developers.facebook.com/docs/instagram-platform/overview); [Business Login](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/business-login)). Long-lived tokens last **60 days**, can be refreshed once they are 24 hours old, and **cannot be recovered once expired** ([refresh reference](https://developers.facebook.com/docs/instagram-platform/reference/refresh_access_token)). Rate limits are 4,800 calls per 24 hours multiplied by the account's impressions in that window, so they are not a concern ([rate limiting](https://developers.facebook.com/docs/graph-api/overview/rate-limiting)). Redirect URIs are the main friction point. Meta historically allowed `http://localhost` only for Development-mode apps and otherwise required HTTPS ([Meta blog, 2018](https://developers.facebook.com/blog/post/2018/06/08/enforce-https-facebook-login/)). Current behaviour for Instagram Login is undocumented, so the connect flow should support an HTTPS local callback (mkcert or a tunnel). Redirect mismatches are the most common self-hosting failure reported for Postiz, which uses the same BYO pattern ([Postiz issue #1155](https://github.com/gitroomhq/postiz-app/issues/1155)).

The terms permit the archive but come with housekeeping. YouTube Analytics and Reporting data and statistics from your own channel may be stored indefinitely, but the client must **check every 30 days that it is still authorized**. Non-statistical metadata such as titles must be refreshed or deleted within 30 days. Revocation must be easy and trigger deletion within 7 days (30 days if the user revokes from Google's side). A privacy policy and YouTube attribution are required. Clause III.E.4.h requires locally computed metrics such as RPM, net subscribers or the project's follower lift to be labelled as not from YouTube ([YouTube Developer Policies](https://developers.google.com/youtube/terms/developer-policies)). The YouTube API terms have **no personal-use exemption** ([YouTube API Services ToS](https://developers.google.com/youtube/terms/api-services-terms-of-service)). Meta's Platform Terms (updated 3 Feb 2026) set no fixed retention period: data is deleted when no longer needed, on user request, or on shutdown. Every app must publish deletion instructions or a deletion callback URL ([Meta Platform Terms](https://developers.facebook.com/terms/); [data deletion callback](https://developers.facebook.com/docs/development/create-an-app/app-dashboard/data-deletion-callback)). A static page in the repo's docs satisfies this for a localhost app.

The terms analysis also undercuts the current collection path. YouTube's Terms of Service forbid accessing the service "using any automated means (such as robots, botnets or scrapers)" ([YouTube ToS](https://www.youtube.com/static?template=terms)). Meta states that "Platform APIs are the only allowable means to access data programmatically" ([Meta Automated Data Collection Terms](https://developers.facebook.com/documentation/development/terms-and-policies/automated-data-collection.md)). Neither carves out reading your own dashboard. Enforcement against a low-volume owner is probably rare, but the downside is losing a creator's main account. The API path is the sanctioned one, and any remaining dashboard reading should be documented as at the user's own risk.

## TikTok and LinkedIn stay on exports and MCP

TikTok's general developer path (Login Kit plus Display API) returns lifetime profile counters (followers, following, likes, video count) and per-video lifetime views, likes, comments and shares. It has **no reach, watch time, profile views or demographics**. Pagination goes back through all public videos at 600 requests per minute, with refresh tokens valid for 180 days ([Get User Info](https://developers.tiktok.com/doc/tiktok-api-v2-get-user-info); [Video Object](https://developers.tiktok.com/doc/tiktok-api-v2-video-object); [token management](https://developers.tiktok.com/doc/oauth-user-access-token-management)). Production access requires app review, and the review guidelines state that **"Apps must not be for private or personal use"** ([App review guidelines](https://developers.tiktok.com/doc/app-review-guidelines)). Running a sandbox app against your own account is the only plausible route, and how long sandbox access remains usable is unverified. Richer organic insights sit in the API for Business Accounts API. Secondary connector documentation describes it as Business-Account-only with a **60-day window** ([Zernio](https://docs.zernio.com/analytics/get-tiktok-account-insights); [Coupler.io](https://docs.coupler.io/sources/category/social-media/tiktok-public/data-overview)). At best, a TikTok connector could take daily snapshots of `views`, `likes`, `comments`, `shares` and `total_followers` and diff them. Everything else in the TikTok catalogue (`profile_views`, viewer splits, play time, LIVE, rewards) stays on exports or MCP.

LinkedIn has the right endpoints behind the wrong gate. `memberCreatorPostAnalytics` provides impressions, members reached, reactions, comments and reshares. From version 2026-04 it adds saves, sends, link clicks, follows and profile views from content. `memberFollowersCount` provides daily follower counts ([Member Post Statistics](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/members/post-statistics); [Member Follower Statistics](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/members/follower-statistics)). Both belong to the Community Management API, which is **"only available to registered legal organizations for commercial use cases"**. It requires a verified business email, website and LinkedIn Page, and rejects personal email addresses ([CM App Review](https://learn.microsoft.com/en-us/linkedin/marketing/community-management-app-review)). A creator with a registered company and Page could apply. Everyone else should keep using the official XLSX export, which covers ranges of 7 to 365 days, through the existing `import_service` ([LinkedIn Help](https://www.linkedin.com/help/linkedin/answer/a701208)).

## The architecture adds connectors beneath the existing service layer

The codebase already has the right layer for this. `SyncService.sync_content`, `sync_account_metrics` and `sync_revenue` accept rows keyed by `metric_key` or GUI label, along with a `source_kind`. They create an `import_batches` row, and both the REST API and `mcp_server.py` already call them. Connectors should therefore be thin adapters: fetch, normalise, and hand rows to `SyncService`. They should contain no persistence logic of their own. The proposal has six parts.

**Connector package.** Add `backend/app/creator/connectors/` with a `base.py` protocol (`connect()`, `backfill(since)`, `sync_daily(through)`, `revoke()`) and one module each for `youtube.py` and `instagram.py`. Each module holds a declarative mapping from API field to `(scope, metric_key, transform)` that mirrors the coverage tables above: minutes ÷ 60, gained − lost, an impression-weighted CTR rollup, and story navigation breakdown values mapped to `story_exits`, `story_forward` and `story_back`. API fields with no catalogue row, such as `engagedViews`, `crossposted_views` and `profile_activity`, should either get new catalogue keys through a seed migration or go to a raw-payload table. Do not drop them. Both platforms add metrics about twice a year and change definitions, so keeping raw JSON per batch (or at least the API version and view-definition epoch) lets you re-derive data later. Use `httpx.AsyncClient` against the REST endpoints rather than the synchronous `google-api-python-client`, which is in maintenance mode ([google-api-python-client](https://github.com/googleapis/google-api-python-client)). `httpx` and `cryptography` already appear in `uv.lock` as transitive dependencies of `fastapi[standard]`, so promote them to direct dependencies rather than adding new libraries. Use `google-auth-oauthlib` only if you want its PKCE loopback helper.

**Provenance.** Add `platform_api` to `SourceKind` (`backend/app/creator/enums.py`) and to the Postgres enum `creator.source_kind_t`. The migration runs `ALTER TYPE creator.source_kind_t ADD VALUE 'platform_api'`. Inside Alembic this needs an autocommit block, because the new value cannot be used in the transaction that adds it. Set `source_label` to something like `youtube_analytics_v2` or `instagram_graph_v26.0` so every fact traces back to an endpoint and version.

**Credentials and tokens.** Client IDs and secrets come from settings or env (`YOUTUBE_CLIENT_ID`, `INSTAGRAM_APP_ID`, and so on). A new `platform_connections` table holds `account_id`, `platform`, the external channel or user id, a Fernet-encrypted refresh or long-lived token (key from env or a file outside the database), `scopes`, `expires_at`, `last_refreshed_at`, `last_verified_at` (for YouTube's 30-day rule), `synced_through` per stream, and RA job ids. FastAPI routes `/oauth/{platform}/start` and `/oauth/{platform}/callback` complete the flow. Use PKCE with a loopback redirect for Google, and an HTTPS-capable callback for Meta. A startup check should report which providers are configured and avoid Postiz's silent failures ([Postiz providers](https://docs.postiz.com/self-host/providers/overview.md)). Revoking calls the platform's revoke endpoint and purges that account's `platform_api` batches, which the YouTube and Meta deletion rules require.

**The `creator-sync` CLI.** Add `creator-sync` to `[project.scripts]` next to `creator-mcp`, with `connect`, `run [--platform] [--backfill]`, `status` and `revoke` subcommands. `run` takes a Postgres advisory lock, refreshes tokens (the Instagram token on every run once it is more than 24 hours old), and pulls from `synced_through` minus a trailing window. Use 7 days for YouTube to absorb its **48–72 hour** AA delay and revisions, and 3 days for Instagram's 48-hour delay. It then upserts through `SyncService`. A full run is idempotent, so running it twice is harmless. First connect triggers a backfill. For YouTube, that means AA month chunks back to channel creation, a Data API pass over the uploads playlist, and **creating the RA reach job immediately**. RA reports are downloadable for only 60 days, so the job must also be polled at least monthly ([RA reports overview](https://developers.google.com/youtube/reporting/v1/reports)). For Instagram, it means 90 days of account metrics in 30-day chunks and lifetime insights for all media, plus a clear message that older daily history is unrecoverable.

**Scheduling.** The default should be an OS scheduler (cron, systemd timer, or Windows Task Scheduler with "run as soon as possible after a missed start") calling `creator-sync run` daily, plus a story poll every 4–6 hours if Instagram stories matter. As an opt-in alternative, an in-app catch-up task in the FastAPI lifespan can run whenever the last successful sync is older than N hours. It shares the advisory lock, so the two mechanisms never collide. With this design, the README's "no outbound connections" and "no background jobs" promises become opt-in statements: nothing leaves the machine and nothing runs unless you configure a connector or a schedule. Ship a template privacy policy and deletion-instructions page, because both platforms require one.

**MCP's new role.** The `sync_*` MCP tools stay unchanged for TikTok, LinkedIn and the API gaps: YouTube unique, new and returning viewers, Instagram profile visits and bio-link taps, follower and subscriber identity lists, and Studio-only views. Add read-only `sync_status` (last run, freshness, token expiry) and `run_platform_sync` tools so Claude orchestrates the connectors instead of reading dashboards.

## Conclusion

The API migration is less about coverage than about the clock. The metrics the APIs lack (Studio's viewer splits, Instagram profile visits and link taps) are second-tier. What cannot be recovered later is history: YouTube impressions before the Reporting job exists, Instagram account metrics older than about 90 days, and every story more than a day old. Once the YouTube connector creates its RA job, the archive stops depending on someone opening Studio. That is why Phase 1 is worth shipping before Phase 2 is polished, and why the RA job should be created at connect time rather than on first sync.

The change also shifts what the project is. A self-hosted archive that calls official APIs makes each self-hoster a "developer" under Google's and Meta's terms, with a privacy policy, a revocation path and labels on computed metrics. A project fed by Claude reading dashboards made none of those demands, but it worked by doing something both platforms prohibit. The connector design keeps Claude useful, since it orchestrates syncs and fills the TikTok and LinkedIn gaps, while moving YouTube and Instagram collection onto a footing the platforms permit and that runs unattended.
