# TikTok rations creator data through sandboxes

A solo creator can get some of their own TikTok data through official channels in late 2026, but much less than from Instagram. Three routes are realistic. The first is a **Login Kit + Display API app left permanently in sandbox mode** with the creator's own account as a target user. It returns lifetime public counters only: followers, following, total likes and video count, plus per-video views, likes, comments and shares. Daily snapshots of those counters turn into a follower and per-video history going forward. The second is the **TikTok API for Business "Accounts API"** (`/business/get/`, `/business/video/list/`). It is the only API with watch time, saves, completion rate, traffic sources, retention curves, demographics and a **60-day daily backfill**. Whether an individual can get its permissions approved, and which metrics a non-Business account receives, are both undocumented. The third is **manual exports**: TikTok Studio's desktop "Download data" (60 to 365 days) and the "Download your data" archive, which holds dated follower lists and wallet transactions. The other official APIs don't fit. Data Portability needs an organisation-style application and is unavailable in sandbox. The Research and Commercial Content APIs serve vetted researchers and EU ad data. Content Posting returns no metrics. Counting the project's 23 TikTok catalogue rows, Display API covers 6 (4 directly, the follower count as a snapshot, and `net_followers` derived from snapshots). The Business API would cover 16 fully and one partially. Six rows (new and returning viewers, the three LIVE rows and estimated rewards) have no API at all. Two rules shape the design. TikTok's review guidelines reject apps "for private or personal use", so production review is off the table. TikTok's US Terms ban automated extraction of data "in any form, for any purpose", so Claude reading the logged-in Studio dashboard is a contractual breach, not a grey area. The project should build a sandbox Display connector now, add exports as the main source of rich metrics, and treat the Business API as an experiment that must be tested live before any design depends on it.

## Display API in sandbox is the only no-review path, and it sees only public counters

The general developer platform has two read endpoints for the authenticated creator. `GET /v2/user/info/` returns fields by scope. `user.info.basic` gives open_id, union_id, avatar URLs and display_name. `user.info.profile` gives bio_description, profile_deep_link, is_verified and username. `user.info.stats` gives **follower_count, following_count, likes_count and video_count**, where `video_count` counts public videos only. The page also warns that "there is a migration plan related to this API" without saying what it is ([TikTok: Get User Info](https://developers.tiktok.com/doc/tiktok-api-v2-get-user-info)). `video.list` pages through the creator's **public** videos newest first, 20 per page, using a millisecond cursor. No lookback limit is stated ([List Videos](https://developers.tiktok.com/doc/tiktok-api-v2-video-list)). Each Video Object carries id, create_time, cover_image_url (**expires after 6 hours**), share_url, video_description, duration, height, width, title, embed links, is_aigc and four lifetime counters: view_count, like_count, comment_count and share_count. It has **no watch time, reach, saves, traffic source or audience field** ([Video Object](https://developers.tiktok.com/doc/tiktok-api-v2-video-object)). Rate limits are 600 requests per minute per endpoint ([Rate limits](https://developers.tiktok.com/doc/tiktok-api-v2-rate-limit)). A daily snapshot of 500 videos costs 26 calls, so quota never binds. Private, friends-only and draft posts are invisible, and a post switched to private simply drops out of the list.

Production access is effectively closed. The App Review Guidelines say, under "Description": **"Apps must not be for private or personal use."** Review also requires a fully developed public website, visible privacy and terms links, and demo videos recorded in sandbox ([App review guidelines](https://developers.tiktok.com/doc/app-review-guidelines)). Passing review would mean presenting a personal archive as a multi-user product. Sandbox mode, launched 24 June 2024, is the workable alternative ([changelog](https://developers.tiktok.com/docs/en/changelog)). An app can have **up to 5 sandboxes**, each with **up to 10 target users**. Target users must be TikTok accounts the developer owns, and they "can be authorized for Login Kit and products that depend on it" with no review ([Add a sandbox](https://developers.tiktok.com/doc/add-a-sandbox)). The sandbox page says nothing about expiry. It also doesn't say whether `user.info.stats` returns real numbers there. A November 2026 open-source issue faces the same uncertainty and records no answer ([Reach-Around #388](https://github.com/ChiefGyk3D/Reach-Around/issues/388)). Because target users are real accounts, sandbox calls very likely return real data. Still, sandbox is a testing feature, and TikTok can restrict it without notice. That risk is a policy risk, not a quota risk.

Token handling is where TikTok differs most from the Instagram setup. TikTok's own pages **contradict each other on lifetimes**. The token-management page, fetched 21 November 2026, says the access token lasts 2 hours and the refresh token 180 days ([Manage user access tokens](https://developers.tiktok.com/doc/oauth-user-access-token-management)). The refresh endpoint's sample response shows `expires_in: 86400` and `refresh_expires_in: 31536000`, which is 24 hours and 365 days ([Refresh a user access token](https://developers.tiktok.com/doc/oauth-refresh-a-user-access-token)). 2026 third-party guides still quote 24 hours and 365 days ([bundle.social](https://bundle.social/blog/oauth-token-refresh-social-apis)). Every refresh **rotates the refresh token**. If the app reuses the old one, "later refresh requests fail and the user must authorize your app again". The prose says the refresh token is valid "180 days after the initial issuance", which suggests re-consent is mandatory on a fixed schedule however often you refresh. For a localhost app, the Desktop Login Kit fits. It requires PKCE with a **hex-encoded SHA-256 challenge** (not the base64url of RFC 7636) and allows `http://localhost` or `127.0.0.1` redirects with a wildcard port. The Web flow demands static https URIs ([Login Kit for Desktop](https://developers.tiktok.com/doc/login-kit-desktop); [Login Kit for Web](https://developers.tiktok.com/doc/login-kit-web)). Users can also decline individual scopes, so the connector must check the `scope` value returned with each token.

The other developer-portal products do not help. The **Data Portability API** exports the "Download your data" archive by API. It needs a separate application, which takes about 3 to 4 weeks, on top of Login Kit approval. The application expects a business-domain email and a live organisation website, and the product is excluded from sandbox ([Data Portability Get Started](https://developers.tiktok.com/doc/data-portability-api-get-started); [Application Guidelines](https://developers.tiktok.com/doc/data-portability-api-application-guidelines)). The **Research API** is limited to qualified academic and non-profit researchers in specific regions ([Research API](https://developers.tiktok.com/products/research-api/)). The **Commercial Content API** covers ad-library data, currently from EU countries only ([Commercial Content API](https://developers.tiktok.com/products/commercial-content-api)). The **Content Posting API** reports only upload status, and unaudited clients can post only privately ([Content Posting Get Started](https://developers.tiktok.com/doc/content-posting-api-get-started)). The changelog shows **no Display API, scope or rate-limit change since 2023**. The USDS Joint Venture, which closed in January 2026, has produced no visible developer-API change ([changelog](https://developers.tiktok.com/docs/en/changelog); [NBC News](https://www.nbcnews.com/business/corporations/tiktok-bytedance-venture-trump-deal-rcna249989)).

## The Business API holds the rich metrics behind an unresolved account-type gate

TikTok groups the Accounts, Mentions, TikTok One, Discovery and Spark Ads Recommendation APIs as its "Organic API". Access starts with a TikTok For Business account and a developer app on business-api.tiktok.com ([About API for Business](https://ads.tiktok.com/help/article/marketing-api?lang=en)). The reference pages are rendered client-side and could not be read, so the field lists below come from TikTok text quoted by connector vendors and from a Go SDK whose comments paraphrase TikTok's docs. Exact key spellings are therefore unverified.

`/business/get/` takes `business_id` (the `open_id` from the Business OAuth token), a `fields` list and inclusive UTC `start_date`/`end_date`. The **maximum lookback is 60 days**, and the default range is the last 7 days ending yesterday ([bububa/tiktok-business SDK](https://pkg.go.dev/github.com/bububa/tiktok-business/model/business)). TikTok's reference, as quoted by Coupler, adds that "any profile data prior to the actual date when TikTok Analytics is enabled won't be available". It also says offline metrics lag **24 to 48 hours** and that counts are taken at the end of each UTC day ([Coupler.io](https://docs.coupler.io/sources/category/social-media/tiktok-public/data-overview)). The daily `metrics[]` array holds:

- video_views, unique_video_views (daily reached audience), profile_views, likes, comments and shares
- daily_new_followers, daily_lost_followers, followers_count and engaged_audience
- audience_activity by hour
- click metrics (bio link, email, phone, address), for Business accounts only

The response also carries 60-day follower splits by age, gender, country and city, each needing **at least 100 followers** ([SDK](https://pkg.go.dev/github.com/bububa/tiktok-business/model/business); [Windsor.ai](https://windsor.ai/data-field/tiktok_organic/)). Likes per day are not reduced by later unlikes. "Reached audience" is limited to ranges of 7 days or less ([Supermetrics](https://supermetrics.com/api/getFields?ds=TIKBA)).

`/business/video/list/` returns **lifetime-only** per-video metrics ([Adverity tips](https://docs.adverity.com/guides/tips-and-best-practices/tiktok-business-tips.html)):

- counters: video_views, reach, likes, comments, shares and favorites (the SDK spells the key `favorities`)
- watch time: total_time_watched in seconds, average_time_watched, and full_video_watched_rate as a ratio such as 0.0395
- new_followers, profile_views and website_clicks attributed to the video
- a per-second `video_view_retention` curve
- `impression_sources` (For You, Follow, Search, Sound and so on)
- `audience_types` (new or returning viewer, follower or non-follower)
- top countries and cities
- a per-second likes curve

([SDK video model](https://pkg.go.dev/github.com/bububa/tiktok-business/model/business/video); [Windsor.ai](https://windsor.ai/data-field/tiktok_organic/)). The official SDK docs give Business tokens a **24-hour access token and a one-year refresh token**, after which "you will need to ask the creator to reauthorize" ([tiktok-business-api-sdk](https://github.com/tiktok/tiktok-business-api-sdk/blob/main/js_sdk/docs/AuthenticationApi.md)). No rate limits, sandbox mode or review timeline were found for these endpoints.

The open question is who may connect. Hootsuite (May 2026) says it "works with TikTok Business accounts only", citing TikTok's API restrictions ([Hootsuite](https://blog.hootsuite.com/tiktok-business-vs-personal/)). Coupler accepts Creator and Business accounts ([Coupler.io](https://docs.coupler.io/sources/category/social-media/tiktok-public/data-overview)). Zernio says personal accounts can read daily account figures, but rich per-video metrics need the Business connection ([Zernio](https://docs.zernio.com/analytics/get-tiktok-account-insights)). The API's own `is_business_account` field implies it reports the account type rather than requiring one. The SDK also limits `profile_views` to Business accounts with completed registration. The most defensible reading is that a Personal/Creator account gets a reduced set, and demographics, reached audience and the richest per-video fields need a Business Account. Switching has a real cost. Business accounts are limited to Commercial Sounds and **lose Creator Rewards Program eligibility**, and some users report losing earlier analytics after switching ([Hootsuite](https://blog.hootsuite.com/tiktok-business-vs-personal/); [Buffer](https://buffer.com/resources/tiktok-creativity-program/)). For a creator earning Creator Rewards, giving up monetisation for API insights is a bad trade.

## Exports carry most of the rest, and the archive fills the account gaps

TikTok Studio Analytics has five tabs: Overview, Content, Viewers, Followers and LIVE. Current Creator Academy guidance reportedly offers **7, 28, 60 and 365-day presets**, with custom web ranges back to **17 July 2022**, and a desktop-only "Download Data" of up to 365 days at a time. Older guidance and many third-party guides still say 60 days ([Sirency, Oct 2026](https://www.sirency.com/blog/tiktok-analytics-explained); [Sozee](https://www.sozee.ai/resources/export-tiktok-analytics-data/)). Both claims are secondary, because TikTok's help pages would not render. One October 2026 practitioner export produced three files. The Content file had one row per video with views, likes, comments, shares, average watch duration, total play time and new followers. The Overview file had daily aggregates, and the Followers file had daily follower counts and demographic snapshots. The same practitioner saw **headers drift between exports** ("Video title" became "Video name"), mixed date formats and truncated titles ([dev.to, knickman](https://dev.to/knickman/i-exported-90-days-of-my-tiktok-analytics-and-joined-the-csvs-the-app-refuses-to-show-you-537p)). No source confirms that the Viewers tab, LIVE tab or estimated rewards are exportable.

"Download your data" (Settings and privacy › Account › Download your data, in TXT or JSON) is a personal-data archive, not an analytics export. It lists posts with received likes but **no view counts**, and follower and following lists with **date and username**. It also has profile counts, watch and search history, LIVE host history (total views, gifters, earnings and likes per session) and **wallet and income transactions** with type, date, currency, amount and status ([Data Portability data types](https://developers.tiktok.com/doc/data-portability-data-types)). Preparation takes up to a few days, and the file stays downloadable for about four days ([PIRG](https://pirg.org/edfund/resources/how-to-request-and-download-tiktok-data/)). It is the only official source of follower identities and the most reliable monetisation ledger.

The table maps all 23 TikTok rows in the seed migration (`backend/alembic/versions/2026_10_29_1244-ad3132ff58f0_initial_schema.py`, lines 124 to 147) to their best source.

| Catalogue row | Display (sandbox) | Business API | Studio export / archive | Manual or agent |
|---|---|---|---|---|
| account `video_views`, `likes`, `comments`, `shares` | Proxy only: sum of public-video deltas | Daily, 60-day backfill | Overview file, daily | — |
| account `profile_views` | — | Daily, Business-registered (conflicting reports) | Overview file | — |
| account `total_followers` | Snapshot of `follower_count` | Daily `followers_count` | Followers file | — |
| account `net_followers` | Derived from consecutive snapshots | `daily_new_followers − daily_lost_followers` | Followers file | — |
| account `total_viewers` | — | Daily uniques only, never summable | Viewers tab (export unconfirmed) | Range values |
| account `new_viewers`, `returning_viewers` | — | Per-video % only | Unconfirmed | Yes |
| content `views`, `likes`, `comments`, `shares` | `view_count` etc., lifetime | Lifetime, 24–48 h lag | Content file | — |
| content `saves` | — | `favorites` | Not reported | — |
| content `total_play_time_sec`, `avg_watch_time_sec` | — | Seconds | Content file | — |
| content `watched_full_pct` | — | Ratio, ×100 | Not reported | — |
| content `new_followers` | — | Lifetime | Content file | — |
| live `unique_viewers`, `peak_concurrent`, `diamonds` | — | — | Archive LIVE totals (partial) | Yes |
| revenue `estimated_rewards` | — | — | Archive wallet ledger (actuals) | Yes |

At the table level, Display fills `accounts`, `account_profile_snapshots` and `content_items` (as `visibility='public'`), plus four `content_metric_facts` keys. The Business API would add daily `account_metric_facts`, the remaining content facts, most of `breakdown_facts` (`age_range`, `gender`, `country`, `city`, `hour_of_day`, `traffic_source`, `viewer_type`, `follower_status`), `comments`, and **`retention_curve_points`**. That last table is one Instagram can never fill. Some tables have no API source at all: `relationships` (fed instead from the archive via `sync_relationships(full_snapshot=True)` with `source_kind=takeout_archive`), `revenue_facts`, `live_sessions`, `interactions` and `content_tags` (which come from parsing captions). Three modelling constraints matter.

- **No TikTok `audience`-scope catalogue rows exist**, yet every breakdown fact needs a `metric_id`.
- **The `followers_3d` view needs a `net_followers` fact for every one of three consecutive days** (`backend/alembic/versions/2026_11_04_1600-793732957eb1_follower_lift_per_post.py`). A connector that skips a day makes post experiments show no data.
- **`sync_service` has no breakdown or retention writer.** Today only `linkedin_service` writes breakdowns.

## US Terms make dashboard reading the riskiest source the project uses

TikTok's US Terms of Service name TikTok USDS Joint Venture LLC and were last updated 15 July 2026. Section 3.4 prohibits using "any automated system or software, including automated 'bots,'" to "scrape, crawl, export or otherwise extract any data or content in any form, for any purpose" without written approval. Section 5.2 lets the JV restrict accounts "at any time and without prior notice" ([TikTok US ToS](https://www.tiktok.com/legal/page/us/terms-of-service/en)). The rest-of-world Terms similarly bar "automated scripts to collect information from or otherwise interact with the Services" ([TikTok ROW ToS](https://www.tiktok.com/legal/page/row/terms-of-service/en)). **Neither has an exception for your own account.** Claude driving a logged-in browser through Studio fits the US wording closely. The realistic downside is action against the account, not a lawsuit. No enforcement case specific to reading your own analytics was found, but losing the creator's main account is a large loss for a small saving.

The sanctioned routes are manual exports, the personal archive, and the Developer Services. Developer Terms Section II.1 expressly allows "automated means in your Application" against the documented APIs ([Developer Terms](https://www.tiktok.com/legal/page/global/tik-tok-developer-terms-of-service/en)). Those Terms, last modified 26 December 2025, set **no cache or retention limit**. They require deleting API-sourced data when the agreement terminates (Section VI). Section III.3(h) bars building databases "on any individual". A creator archiving their own authorised data arguably falls outside that clause, but that is an interpretation, not a ruling. Data the user downloads by hand is their own copy and is not subject to the deletion duty. One discrepancy remains. Open Terms Archive reports a new "TikTok Developer US Data Sharing Agreement" section added in January 2026 ([Open Terms Archive](https://opentermsarchive.org/en/memos/tiktok-rewrites-all-terms-following-usa-operations-transfer/)), but the Developer Terms page fetched for this research showed no US-specific section. Its contents, if it exists, are unknown.

## Build a sandbox snapshotter first and let exports do the heavy lifting

The architecture follows from what each source can and cannot do. Every component writes through the existing `SyncService`, so the connector stays a thin adapter.

**Display connector.** Ship a Display connector, run as a sandbox app owned by each self-hoster, under `backend/app/creator/connector/tiktok/`. It uses Desktop Login Kit with hex-encoded PKCE and a localhost redirect, and requests the scopes `user.info.basic`, `user.info.profile`, `user.info.stats` and `video.list`. Tokens go in an encrypted `platform_credentials` table, not in `.env`. The connector saves each rotated refresh token in the same transaction as the refresh response, logs `expires_in` and `refresh_expires_in` on every refresh, and shows the re-consent date in the "Expiring soon" panel.

**Daily run.** At a fixed UTC time (for example 00:15), the job:

- records one profile snapshot
- runs a full `video.list` crawl with `full_snapshot=True`, treating "missing" as "deleted or hidden"
- downloads thumbnails immediately, because cover URLs expire after 6 hours
- stores the counters as append-only `lifetime` facts
- writes a `net_followers` day fact derived from consecutive follower snapshots, labelled as derived, so `followers_3d` works

Per-video daily deltas should come from a view using `LAG()` over `captured_at`. They should not be stored as `lifetime` rows, because `v_content_summary` takes `max()` over those. Videos under 72 hours old can get extra `video.query` snapshots every 6 hours.

**Imports.** Add a Studio CSV/XLSX importer that matches headers by alias and tolerates drift. Route `PK` files by sheet names, since today every XLSX goes to LinkedIn. Add an archive importer for follower lists and wallet transactions, run monthly. Claude's role changes from reading dashboards to parsing files the user downloads.

**Business API.** Keep it as a feature-flagged second client, added only after a live test shows an individual can get the permissions and the creator's account type returns the needed fields. If it works, re-pull the last 4 days of `/business/get/` daily. Fetch breakdowns and retention daily for videos under 30 days old and weekly for the rest.

**Schema changes.** One migration, shared with Instagram, should:

- add `platform_api` and `derived` to `SourceKind`
- add TikTok audience-scope keys (`follower_share`, `active_followers`, `viewer_share`)
- add account keys (`new_followers_daily`, `lost_followers`, `engaged_audience`, `bio_link_clicks`, `total_likes`, `video_count`)
- add content keys (`reach`, `profile_views`, `website_clicks`)
- add `sync_breakdowns` and `sync_retention` writers

The catalogue's `retention_days=365` matches the current Studio range selector, so keep it. Record the 60-day API window separately, so `v_expiring_metrics` warns at the right time for each source.

Several facts must be settled by live calls before code depends on them.

| Needs a live test | How to settle it |
|---|---|
| Sandbox returns real `user.info.stats` and full `video.list` data | Create a sandbox, authorize your own account, call both endpoints and compare with the app |
| Token lifetimes (2 h/180 d vs 24 h/365 d), in sandbox and production | Log `expires_in` and `refresh_expires_in` from the first token and the first refresh |
| Whether refreshing extends the refresh token or it runs from first issue | Compare `refresh_expires_in` across refreshes over a few days |
| Sandbox expiry, inactivity cleanup, and a reported cap of 5 authorizations per 24 h | Keep the sandbox running for weeks and watch for revocation |
| Desktop PKCE with hex challenge and a `127.0.0.1:*` redirect | First authorization attempt |
| `video.list` depth for a full catalogue, and whether a video made private drops out | Crawl to the end, then toggle one test post to private |
| Business API: whether an individual's app is approved, and which fields a Personal/Creator account returns | Register a developer app and request the TikTok Accounts permissions before deciding whether to switch account type |
| Business API key names (`favorites`/`favorities`, `daily_total_followers`), percent scale, units of `total_time_watched` | Compare one video against Studio |
| Display `id` equals Business `item_id` | Compare on the first video |
| Studio export columns, the 60 vs 365-day limit, and whether Viewers, LIVE and rewards are exportable | Download every section once and inspect the files |
| Archive follower-list format (dates, usernames) | Request one JSON archive before writing the parser |

The contrast with Instagram is sharp. The Instagram connector already runs on an **unpublished Standard Access Meta app with no review**, using a **system-user token that never expires**. Its probe passed 61 checks with zero failures, and 24 of the 25 Instagram catalogue rows can come from the API, including roughly 90 days of account-metric backfill (see `reports/Instagram connector findings.md`). TikTok offers a sandbox that may run indefinitely or may not. It has refresh tokens that rotate and expire within 180 or 365 days, and 6 of 23 rows from the API path that is actually available. The richer path needs an approval no individual has been documented as receiving, and possibly a change of account type that costs monetisation. Instagram's connector can replace dashboard reading. TikTok's can only replace part of it.

## Conclusion

Each TikTok source gives up something different. Display gives freshness and an unbroken series but little depth. The Business API gives depth but only 60 days of memory and uncertain access. Exports give depth and a longer range, but the user has to download them. The archive gives identities and money but no metrics. So the project's TikTok history will always be stitched together from several sources. That makes the batch-level `source_kind` and `source_label` provenance central to the design. Each fact needs to say which source produced it, because the same metric key will hold values that differ by 24 to 48 hours of lag and by public-only versus all-post scope.

The clock matters more than coverage here too. The Business API forgets after 60 days, and Display stores nothing before the first snapshot. The sandbox snapshotter costs little and fills the `followers_3d` gap at once, so start it now. Every day it doesn't run is history that only a manual export can partly recover. The Business API decision should wait for a live test, not for more research. The deciding facts (whether an individual is approved, and what a Creator account returns) are not published anywhere, and an afternoon with a developer account will settle them.
